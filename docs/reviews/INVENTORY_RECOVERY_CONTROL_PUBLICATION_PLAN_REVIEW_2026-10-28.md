# Durable stop/resume publication plan review — 28 October 2026

## Disposition

The control-publication plan now names the required trust boundary and recovers
each publication cut. It is ready to guide a prospective implementation, but
it is not an implemented host control service, a runtime admission, or release
approval. TX3b stays open until the witness and public factory are real and the
native crash matrix passes.

## Code trace and failure model

`runtime_predicates.RuntimeLeaf.__call__` requires both a fixed external
admission callback and a control-evidence callback. It passes the latter to
`stop_authority.verify`. The reader checks the transfer-time stop floor, every
sequence and previous-identity link, each current `user-stop.json` byte string,
and each resume against the exact latest stop. It is read-only by design.
This is a useful consumer contract; it supplies no authenticated producer.

The current `inventory_recovery_v2.control.stop` writes a standalone stop file.
Its resume check verifies the file hash and literal `authorized_by`/action
strings. `control_history.advance` protects a different cancellation-retirement
transaction. Neither provides an independently retained monotonic witness for
the runtime stop history. The v3 runtime-predicate fixture writes a JSON object
and then projects stop/resume files directly; it explicitly labels itself a
fixture, not a production trust source. Public execution remains blocked, which
is correct until a real producer and factory are composed.

The first plan draft treated an external directory as an independent head.
That is insufficient if the worker UID can rewrite or roll back that directory.
The revised plan requires a host-protected broker/witness with an atomic
sequence/head compare-and-swap API, authenticated responses, a complete retained
pending command, a read-only runtime capability, and an exact host-authorized
write capability. If that isolation cannot be demonstrated, production stays
blocked. This limitation is explicit: the design cannot protect against an
administrator who can roll back the witness itself.

## Transaction/corner-case review

The revised order is crash recoverable:

1. The broker authenticates and durably retains the complete pending event
   before any workspace stop/resume projection changes. A crash before the
   local intent can therefore reconstruct only the exact host-authorized event.
2. The local intent/event, each projected file and parent directory, and the
   local committed head are fsynced in order. Until the broker commits the new
   head, its pending state vetoes every runtime reader.
3. Broker commit happens after all local projections. A crash after local
   commit but before broker commit remains vetoed and can be repaired from the
   broker's retained event; a crash after broker commit is an exact idempotent
   replay.
4. Reads verify a stable authenticated broker snapshot before and after
   reading the event prefix and workspace projections. Races veto/retry. Missing
   state, unknown projection bytes, rolled-back workspace state, replayed broker
   state, and symlink aliases fail closed; the reader never reconstructs state.

The test matrix covers initial and inherited stops, exact explicit resume,
multiple stops, process death around intent/event/witness/projection/commit,
repeated cold repair, stop/resume races, lost or rolled-back files, forged or
stale commands, duplicate IDs, path aliases, permission errors, and storage
failure. Add one test at implementation time for witness replay with a stale
challenge, since a valid signature on an old snapshot alone does not prove a
fresh monotonic read. The host broker must bind a client nonce and return a
signed/authenticated snapshot containing it.

Request IDs and exact command bytes bind idempotency. Stop timestamps must be
generated by the trusted writer and strictly increase; if its trusted clock
rolls backward or cannot produce a valid next time, it must refuse the write
rather than accept caller-supplied time. Resume must never erase the current
stop; it records authorization over the latest exact stop and original root
contract. A later stop invalidates the resume.

## Entry gates and unresolved work

The implementation must first agree a fixed host-owned witness interface and
provisioning/action identity. The public `configuration` command may derive
the path and verify a read-only signed view; it must never initialize the
witness. Only a separately approved host action can install/initialize or
publish controls. Before production admission, exercise the actual public
`RuntimeLeaf` and monitor construction with the root-owned service, cold process
restart and process-death cuts. Keep all current fixture callbacks explicitly
test-only. Do not infer permission from the external directory, a digest chain,
an `authorized_by` field, or this plan review.

No host witness is installed and no production execution was attempted in this
review. The executor gate passed independently of the control plan. The plan
review does not change release status or authorize ZLB continuation.
